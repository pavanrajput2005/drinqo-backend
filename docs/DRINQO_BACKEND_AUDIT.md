**Post-fix verification:** 309 selected behavioral tests passed on disposable SQLite, with migrations disabled and outbound provider HTTP blocked. No model drift. Generated schema assertions passed for bearer authentication on staff confirmation and the Apple login response. The synthetic production security-tagged deployment check now reports only HSTS subdomain and preload advisories; neither should be enabled without domain-owner review. These checks do not replace a PostgreSQL contention run or hosted acceptance.

**Decision: hold internet-facing staging with real users, identity documents or payments.** The backend has a functioning, tested customer authentication and staff-handover core. It also has a failing payment webhook, inconsistent payment guidance, unsafe inventory writers, and incomplete deployment configuration. A successful Django system check is not a release gate for these failures.

**Scope and evidence.** Paths below are relative to `D:\drinqo_backend`. Reviewed the active URL tree (`config/urls.py`), application models, migrations, permissions, serializers, services, routes, tests and deployment settings. Compared the final auth/Flutter handoffs with the order-placement audit, six-issue handoff and Shop/Super Admin contracts. The archived shop-admin patch and historical OTP suites are not the running API. This is source review plus selected isolated tests, not a certification of every branch, deployed provider, Flutter build, database row or infrastructure control. No application changes, shared database access, migration execution, credential inspection or deployment were needed.

## Database, security and unresolved risks

- **Integrity present:** case-insensitive email uniqueness and unique social subjects (`accounts/models.py:10–59`); unique product per cart (`customers/models.py:155–185`); one payment and one staff confirmation per order plus positive amount, exact split, INR and refund constraints (`orders/models.py:291,333–357,393–394`). FK and unique indexes plus a case-work index exist. This is not query-plan or load-test evidence.
- **Migration/data preservation:** `accounts/migrations/0011_mobile_auth.py:6–22` checks for normalized-email collisions before backfill and adding uniqueness. Actual legacy duplicates, pending migrations, table sizes and restore time are **unknown**. Do not auto-merge identities. `shop_admin/models.py:36,56` and `shops/models.py:6,71` define distinct shop/document tables. Active product and order flow uses the latter; legacy/profile/document callers must be mapped before retiring either.
- **Concurrency requiring PostgreSQL:** shop-then-order locking in `orders/locking.py:7–15`, order-first cancellation in `orders/views.py:359–398`, and joined locks on older paths warrant a contention test. This is not a confirmed deadlock. Validate checkout, cancellation, inventory, refund callbacks, simultaneous OTP and handover against an explicitly disposable PostgreSQL target. Query plans for paginated order history, nearby shop discovery, reports and stock operations remain unmeasured.
- **Lifecycle gaps:** order creation reserves inventory by decrement and clears cart (`orders/views.py:260–292`); no create-order replay key or timed unpaid-stock release was found. A timeout is ambiguous to the caller. Agree reservation/expiry rules before adding a worker; any expiry must coordinate with captures, refunds and already-approved orders. `ShopStaff` removal is recorded in `shop_admin/migrations/0006_delete_shopstaff.py`; do not infer employee delegation from the word “staff.”
- **Access and sensitive data:** inspected customer/order ownership filters, owner-scoped shop operations, Super Admin role check, JWT block checks, masks, no-store handover responses and signed payment evidence. No SQL injection or cross-shop handover bypass identified in the inspected paths; ORM filters predominate and no direct raw SQL call was found by the active-app source scan. This is not proof of universal IDOR resistance. Age proof/license storage requires private serving independent of URL authorization; location is a client assertion. Confirm retention and proxy/APM redaction for uploads, coordinates, auth and payments.
- **Abuse controls:** email OTP has both DB and request limits; password/social endpoints have scoped limits. `accounts/views.py:77–81` public registration has no route throttle and `config/settings.py:439–469` configures rates but no global throttle class. Test rate limits across workers with a shared cache and trusted proxy identity; consider explicit registration and refresh budgets. A clean dependency check does not establish absence of CVEs.

## Prioritized roadmap and release decision

1. **First approval batch — money, account ownership and stock:** A01–A07. Start with the already-failing webhook regression and payment projection; ship identity recovery changes only after agreeing how legacy users retain access. Test contention on PostgreSQL before accepting stock changes.
2. **Second batch — trustworthy contracts:** fix validation, push registration and schema (A08–A12); reconcile old test expectations (A13). Align customer, Shop Admin and Super Admin documentation to the current routed API. Establish one release suite; do not mask failures by removing negative authorization tests.
3. **Infrastructure batch:** close D01–D05 using an isolated staging domain, synthetic accounts, private media and Razorpay **test** credentials. Independently review migration plan, backup and restore before approving a database rollout. Keep real merchant activation separate.
4. **Release rehearsal:** both pickup modes from registration through cancellation/refund or completion; fee-boundary approval; blocked/inactive, foreign owner, expired license, duplicate webhooks, simultaneous completion, password recovery and app restart. Record expected vs observed outcomes with redacted logs.

**Readiness estimate by evidence:** dependency consistency and model-to-migration drift checks pass; behavioral acceptance is partial; payment/error-path correctness fails; multiwriter PostgreSQL safety is unverified; deployment security/packaging is not ready; external integrations and recovery are unverified. **No-go for public staging.** A private synthetic QA environment is an appropriate next milestone once ingress, packaging and private storage are isolated. No credible percentage or release date follows from a selected-test pass rate.
